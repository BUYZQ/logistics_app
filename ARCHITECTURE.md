# Архитектура проекта `logistics_app`

## 1. Общее описание

Проект состоит из двух основных частей:

- `Flutter`-клиент для операторов и экспедиторов
- `FastAPI`-бэкенд для авторизации, заявок, чатов, сотрудников и админ-панели

Система предназначена для управления логистикой: создания заявок, назначения экспедиторов, отслеживания маршрута, общения в чатах и работы с профилем сотрудника.

## 2. Технологический стек

### Мобильный клиент

- `Flutter`
- `Dart`
- `go_router` — маршрутизация
- `http` — REST-запросы к backend
- `shared_preferences` — хранение токена, темы и данных пользователя
- `yandex_mapkit` — отображение карты и маршрута
- `image_picker` — выбор изображения из галереи
- `url_launcher` — телефонные звонки и внешние ссылки
- `intl` — форматирование дат и времени
- `google_fonts` — кастомные шрифты
- `flutter_launcher_icons` — генерация иконки приложения

### Backend

- `Python 3.11`
- `FastAPI` — HTTP API
- `Uvicorn` — ASGI-сервер для запуска
- `Gunicorn` — вариант запуска в production
- `SQLAlchemy` — ORM и работа с БД
- `Pydantic` — схемы запросов и ответов
- `python-jose` — JWT токены
- `python-dotenv` — загрузка конфигурации из `.env`
- `httpx` — интеграция с внешним SMS API
- `aiosmtplib` — отправка email
- `sqladmin` — административная панель
- `itsdangerous`, `SessionMiddleware` — сессионная авторизация админки

### База данных

- Основной дефолтный вариант: `SQLite` (`nekst.db`)
- Поддерживается `PostgreSQL` через `DATABASE_URL`

## 4. Архитектура Flutter-клиента

### 4.1 Слои

Клиент реализован достаточно просто, без отдельного state-management фреймворка вроде `Bloc`, `Riverpod` или `Provider`.

Используются три основных уровня:

- `UI / Screens` — экраны и виджеты
- `Services` — запросы к backend
- `Models` — структуры данных приложения

### 4.2 Папки и ответственность

#### `lib/app`

Содержит глобальную конфигурацию приложения:

- `app.dart` — `MaterialApp.router`
- `router.dart` — маршруты и редиректы по роли пользователя
- `theme.dart` — светлая/темная тема
- `shell_scaffold.dart` — нижняя навигация и бейдж непрочитанных сообщений

#### `lib/core/models`

Доменные модели клиента:

- `user.dart` — пользователь и `AuthState`
- `order.dart` — заявка и статусы
- `message.dart` — чат-комнаты и сообщения

#### `lib/core/services`

Слой связи с backend:

- `api_service.dart` — auth, токен, профиль, загрузка аватара
- `order_service.dart` — получение, создание и обновление заявок
- `chat_service.dart` — комнаты, сообщения, счетчик непрочитанных

#### `lib/features`

Фича-ориентированная структура экранов:

- `auth/` — вход по OTP
- `orders/` — список, создание, детали заявки
- `expeditor/` — экран экспедитора и подтверждение доставки
- `chat/` — список чатов и окно переписки
- `map/` — маршрут на карте
- `profile/` — профиль и настройки

### 4.3 Навигация

Навигация построена через `go_router`.

Логика:

- если пользователь не авторизован, доступен только `/login`
- после входа:
  - `operator` попадает в `/orders`
  - `expeditor` попадает в `/expeditor`

Используется `StatefulShellRoute` с нижней навигацией:

- вкладка заявок
- вкладка чатов
- вкладка профиля

### 4.4 Хранение состояния

В проекте нет централизованного state store.

Сейчас состояние хранится так:

- токен — в `SharedPreferences`
- данные пользователя — в `SharedPreferences`
- текущий пользователь — в статическом `AuthState.currentUser`
- количество непрочитанных — через `ValueNotifier<int>`
- локальное UI-состояние — в `StatefulWidget`

Это подходит для небольшого проекта, но при росте логики начнет усложнять поддержку.

### 4.5 Работа с сетью

Клиент общается с backend по REST API.

Особенности:

- `baseUrl` захардкожен в коде
- авторизация передается через `Authorization: Bearer <token>`
- для загрузки аватара используется `multipart/form-data`
- чат обновляется polling-механизмом каждые 3 секунды

### 4.6 Работа с картами

Для маршрута используется `Yandex MapKit`.

На Android:

- ключ карты читается из `local.properties`
- прокидывается через `BuildConfig`
- инициализация идет в `MainApplication`

Карта показывает:

- точку отправления
- точку доставки
- прямую линию маршрута между ними

### 4.7 Работа с файлами и медиа

- `image_picker` используется для выбора аватара
- также пакет подключен для фото при подтверждении заказа
- на Android запрошены разрешения на камеру, медиа и интернет

## 5. Архитектура backend

### 5.1 Общая схема

Backend построен как монолитный FastAPI-сервис.

Основные части:

- HTTP API
- ORM-модели
- схемы сериализации
- сервисы внешних интеграций
- HTML dashboard
- admin-панель через `sqladmin`

### 5.2 Точка входа

Файл `backend/app/main.py`:

- создает `FastAPI` приложение
- включает `CORS`
- подключает `SessionMiddleware`
- подключает `sqladmin`
- монтирует `uploads/`
- регистрирует роутеры
- на старте вызывает `init_db()`

### 5.3 Роутеры

#### `auth.py`

Отвечает за:

- отправку OTP
- проверку OTP
- выдачу JWT
- получение текущего пользователя

#### `employees.py`

Отвечает за:

- создание сотрудников оператором
- список сотрудников по складу
- просмотр сотрудника
- деактивацию сотрудника
- получение списка складов

#### `orders.py`

Отвечает за:

- список заявок
- создание новой заявки
- обновление статуса и данных экспедитора

#### `chat.py`

Отвечает за:

- список чатов текущего пользователя
- создание или получение комнаты
- получение истории сообщений
- отправку сообщения

#### `upload.py`

Отвечает за:

- прием изображения
- сохранение файла на диск
- запись URL аватара в профиль пользователя

#### `dashboard.py`

Отвечает за:

- HTML dashboard
- JSON-статистику по заказам, пользователям, складам и чатам

### 5.4 Сервисы

#### `sms_service.py`

Интеграция с `sms.ru`.

Назначение:

- отправка OTP по номеру телефона
- в dev-режиме выводит код в консоль, если `SMSRU_API_ID` не задан

#### `email_service.py`

Интеграция с SMTP.

Назначение:

- отправка OTP на email

Важно:

- сейчас реализация фактически работает как dev-заглушка и печатает код в консоль
- реальная отправка письма в текущем виде не доходит до рабочего участка функции из-за раннего `return True`

- `pending`

Хранит чат по заказу:

Хранит сообщения:

## 7. Авторизация и безопасность

### 7.1 Пользовательская авторизация

Сценарий:

1. Оператор создает сотрудника
2. Сотрудник вводит телефон или email
3. Backend отправляет OTP
4. Сотрудник подтверждает код
5. Backend выдает JWT
6. Клиент сохраняет токен локально

### 7.2 JWT

Используется:

- `python-jose`
- payload с `sub`, `exp`, `iat`

Токен используется для доступа к защищенным endpoint.

### 7.3 Админка

Есть отдельная admin-аутентификация через session middleware.

Важно:

- логин/пароль сейчас захардкожены как `admin/admin`
- это допустимо только для локальной разработки

### 7.4 Текущие ограничения безопасности

- `CORS` открыт на `*`
- `SECRET_KEY` имеет небезопасные дефолтные значения
- токен хранится в `SharedPreferences`
- админка защищена упрощенно
- загрузка файлов сохраняет их на локальный диск без отдельного object storage

### Оператор

- входит по OTP
- просматривает список заявок
- создает новую заявку
- просматривает детали заявки

## 11. Замеченные архитектурные особенности и техдолг

### Что уже хорошо

- разделение на frontend и backend
- понятная feature-структура Flutter
- backend разбит по доменам
- есть роли пользователей
- есть admin/dashboard
- есть подготовка к PostgreSQL

### Что ограничивает масштабирование

- нет полноценного state management на клиенте
- `baseUrl` захардкожен
- чат работает через polling, а не WebSocket
- SQLite используется как базовый режим
- миграции не оформлены через полноценный `Alembic` workflow
- часть бизнес-логики и доступа завязана на простые проверки в роутерах
- фото заказов хранятся в строковом поле
- email-отправка фактически находится в режиме заглушки

### Что стоит улучшить в первую очередь

1. Вынести конфигурацию клиента и сервера в нормальные env/config слои
2. Перевести production БД на PostgreSQL
3. Настроить реальные миграции через Alembic
4. Убрать dev-заглушки из email/admin/security
5. Перевести чат на WebSocket или SSE
6. Добавить централизованное управление состоянием в Flutter
7. Вынести медиа в отдельное хранилище или отдельную сущность
8. Добавить автоматические тесты API и клиентской логики

## 12. Краткий вывод

Проект уже представляет собой рабочую прикладную систему с мобильным клиентом и backend API.

Сейчас архитектура ориентирована на быструю прикладную разработку:

- простой Flutter UI
- прямые REST-вызовы
- монолитный FastAPI backend
- SQLite по умолчанию
- локальное хранение файлов

Для MVP или внутреннего корпоративного приложения это нормальная база.
Для production-эксплуатации с ростом пользователей проекту понадобятся усиление безопасности, конфигурации, миграций, хранения файлов и сетевой архитектуры чата.
